# Event participation roles

The event detail page presents four role cards, each linking directly to its registration form: athlete (`ATHLETE`), referee (`REFEREE`), team leader (`TEAM_LEADER`) and coach (`COACH`). Ordinary participant (`ATTENDEE`) and medical staff (`MEDICAL_STAFF`) are no longer available for event registration; historical records remain readable. The registration page shows event name, date, location and deadline, then a role summary with a change action and the relevant form. The standalone role picker uses descriptive cards instead of a dropdown. Existing links with `mode=individual` or `mode=group` continue to open the original athlete registration UI and flow. Signed-in athletes with a linked athlete profile can use that profile for direct registration or switch to the full individual/team form. Both light and dark layouts adapt to mobile screens.

Non-athlete applications use `EventParticipation`, independently of athlete competition registrations and account type selections. Guests enter contact details; signed-in applicants use their account name/email. Coaches, team leaders and referees must provide a CCCD or passport number, the corresponding document uploads (both sides for CCCD) and a portrait. Team leaders must also select their unit / club; coaches and referees may select one. Unit selections use the event's participating federation list when configured. Applications begin as `SUBMITTED`, with a unique reference code. One email can register multiple roles, but cannot submit the same role twice at the same event. Selecting a role does not grant CMS or scoring access.

Document numbers are encrypted. Uploaded portraits and identity documents are stored privately through `EventParticipationMedia`, and temporary upload references are consumed when the application is submitted. CMS reviewers can inspect document numbers and download files through authenticated admin endpoints. Public ticket and QR data exclude document numbers, identity images, email and phone. A portrait becomes publicly accessible only while the application is `CONFIRMED`; revoking a ticket also revokes its public portrait access.

Applicants can view athlete and non-athlete tickets together in the "Thẻ & hồ sơ đã đăng ký" tab at `/account`; its count includes both kinds. Confirmed coach, referee and team-leader applications display their actual card with separate view, print and PDF download actions. CMS event pages list these three roles in the "Thẻ" tab, with keyword, role and status filters alongside the shared card designer. The designer can preview each role. CMS users review applications at `/cms/registrations`, including event-specific links from the card list. Review records the status, reason, timestamp and reviewer. The existing athlete registration, identity, disciplines, payment and ticket flow stays in `AthleteEventRegistration`.

All roles receive an A6 PDF ticket with their role, portrait, unit and QR code once confirmed. The shared web and PDF design supports a dynamic `ROLE` text field; older templates with the default athlete title remain compatible. Applicants (including guests) and CMS users open `/tickets/<referenceCode>` and download through the shared `/participant-auth/tickets/<referenceCode>/pdf` endpoint. Confirmation atomically enqueues an email with the PDF attachment through the existing SMTP settings, retry queue and background worker. Repeated confirmation does not enqueue another email; revoked applications cannot download official tickets and queued emails are skipped. Migration `20261010130000_participation_ticket_email` queues tickets for previously confirmed role applications. Non-athlete applications have no competition fee; athlete payment rules are unchanged.

The print action opens `/tickets/<referenceCode>?print=1`. It waits for the QR code, card images and fonts, then checks the current ticket status from the API before opening the browser print dialog. Invalid status, request failures or failed images prevent printing and offer retry/PDF actions. The browser print layout uses an A6 sheet (105 × 148 mm) and omits navigation, footer, controls and private profile details.

When `IDENTITY_OCR_ENABLED=false`, uploaded athlete and non-athlete identity documents are automatically marked `VERIFIED`, including PDF uploads. Turning off OCR in system settings also verifies existing pending identity documents. This document verification does not automatically confirm a non-athlete event application or issue its ticket; CMS approval remains required.

Apply the existing participation migrations and `20261013090000_event_participation_identity` with `npm run prisma:deploy`, then regenerate the client with `npm run prisma:generate` before running the updated backend. Verification: build both apps and run frontend lint. Run `node tests/regression/event-participation-tickets.mjs` to check role labels, portraits, A6 PDFs, legacy templates, QR privacy and revoked access without a database. Run `tests/integration/event-participation-live.cjs` inside the local backend container for registration roles, required identity/photos, optional referee units, required team-leader units, upload consumption, privacy, review permissions and event registration windows; it creates and removes isolated fixtures.
